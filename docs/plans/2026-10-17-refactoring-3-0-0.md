# Plan: Refactoring 3.0.0 (verhaltensgleich)

Stand 17.10.2026. Arbeitskopien `metadata-agent-3` und
`metadata-agent-webcomponent-3` (Kopie von 2.1.1, `.git` mitkopiert, keine
Commits). Die Originale bleiben unberührt.

## Ziel

Die vier großen Dateien nach Zuständigkeit aufteilen, ohne Verhalten, API oder
Konfiguration zu ändern. Version 3.0.0 markiert den neuen Aufbau.

## Kontext

| Datei | Zeilen | Zuständigkeiten heute |
|---|---|---|
| `src/main.py` | 3.530 | App-Aufbau, Middleware, Lifespan, OpenAPI, Fehlerantworten, 26 Endpunkte in 10 Bereichen |
| `src/services/llm_service.py` | 2.107 | Durchsatz-Gates, HTTP-Transport mit Auth/Retry/Fehlerzuordnung, Prompt-Aufbau, Wertnormalisierung (Datum, Zahl, Vokabular …), Inhaltsart-Erkennung, Feld-Orchestrierung |
| `src/services/repository_service.py` | 1.968 | Vorschaubild laden, Konfiguration/Hilfen, Node anlegen/verwerfen, Metadaten schreiben, Upload- und Save-Abläufe, Prüfen und Workflow |
| `src/core/canvas.service.ts` (Widget) | 1.225 | Zustand, drei Extraktionsabläufe, Feldzustand, Metadaten-Export, Wert-Cache je Inhaltsart, Fehler-/Warnmeldungen |

## Umfang

Drin: Aufteilen dieser vier Dateien; Testanpassungen nur dort, wo ein Test ein
verschobenes Modul-Attribut patcht (Patch-Ziel ändern, Prüfung unverändert);
Version 3.0.0; Doku zur Modulstruktur.

Nicht drin: neue Funktionen, geänderte Endpunkte, Antworten, Logs, Metriken
oder Einstellungen; Umbau langer Einzelfunktionen (z.B. `_build_extraction_prompt`,
`upload_metadata`) – sie wandern unverändert und stehen als Folgearbeit unten.

## Ansatz

| | Wie | Für | Gegen |
|---|---|---|---|
| A: Mixins in eigenen Modulen | Methoden ziehen unverändert in Mixin-Klassen je Zuständigkeit; `LLMService`/`RepositoryService` erben sie | gleiche Attribute und Aufrufe (`service._call_llm`, `service.http_client = …`), Tests bleiben fast unverändert, Code wird verschoben statt umgeschrieben | eine Klasse über mehrere Dateien; Zustand bleibt geteilt |
| B: Komposition | eigene Objekte (Client, PromptBuilder, Normalizer), Service delegiert | klarere Grenzen | viele Testanpassungen, mehr neuer Code, höheres Risiko |
| C: nur Funktionen auslagern | reine Hilfsfunktionen auf Modulebene | einfach | lässt Transport und Abläufe in der großen Datei |

**Gewählt:** A für die Python-Services (geringstes Risiko bei gleichem
Wartungsnutzen; Komposition kann danach schrittweise folgen), FastAPI-Router
für `main.py`, reine Funktionen/kleine Klassen für das Widget (B/C-Mischung,
weil Angular-Services ohnehin per DI zusammengesetzt werden).

## Globale Regeln

- Python 3.13, FastAPI, ruff 0.15.5; Angular 21 (nicht 22).
- Code-Kommentare englisch, Doku deutsch (Projektkonvention).
- Verschieben heißt verschieben: kein Umformulieren von Meldungen, keine
  Logikänderung im selben Schritt.
- Alte Importpfade bleiben gültig: alle öffentlichen Namen von 2.1.1 werden
  aus `llm_service.py` und `repository_service.py` re-exportiert
  (`tests/test_import_compatibility.py`); `_`-Helfer sind intern.
- Folge der öffentlichen Namen in `repository_support`: `screenshot_service.py`
  importiert `get_repository_config` statt `_get_repository_config` (gleiches
  Objekt; der alte Name bleibt als Alias).
- Abhängigkeiten zur Laufzeit über ein Modul nachschlagen (`deps.settings`,
  `deps.get_metadata_service(...)`), damit `monkeypatch` weiter greift.
- Widget-Deploy immer mit `--target=../metadata-agent-3/src/static/widget`
  (der Default zeigt auf das Original).
- Keine Commits, kein Push.

Router-Reihenfolge = heutige Reihenfolge der Endpunkte (die Spec bleibt gleich).
Deshalb eigene Router für `/validate`+`/export/markdown` (sonst wäre `generate.py`
~800 Zeilen) und für `/upload/verify` (steht in der Spec nach `/screenshot`).
Von mehreren Routern genutzt: `SAVE_NODE_ERROR_STATUS` (`responses.py`),
`require_node_id` (`deps.py`). FastAPI ≥ 0.142 legt eingebundene Router als
einen Eintrag in `app.routes` ab; die tatsächlichen Routen liefert
`fastapi.routing.iter_route_contexts` (Chart-Test, Charakterisierung).
Logger-Namen folgen den Modulen (`src.api.responses` statt `src.main`) –
im CHANGELOG nennen.
Abhängigkeit: `routers → deps/responses → services`; `main → api`. Kein Router
importiert `main`.

Die öffentliche API von `CanvasService` bleibt; Specs, die private Methoden
aufrufen, testen danach die Funktion direkt.

Umgesetzt ohne `field-value-cache.ts`: Der Wert-Cache ist eine `Map`, die die
`InstanceRegistry` zwischen Komponenten derselben Instanz teilt; eine eigene
Klasse hätte den Vertrag der Registry geändert. `applyValueToField` bleibt im
Service (braucht Schema und ShapeExpander, eine Spec ruft ihn direkt).
`canvas.service.ts` 1.225 → 1.014 Zeilen; der Rest sind vor allem die drei
fast gleichen Extraktionsabläufe (Folgearbeit).

## Nicht-funktional

Keine Änderung an Performance, Sicherheit, Logs, Metriken, i18n oder Barrierefreiheit.

## Risiken

| Risiko | Gegenmaßnahme |
|---|---|
| Patch greift nach dem Verschieben nicht mehr, Test prüft dann ins Leere | Patch-Ziele vorab inventarisiert; Laufzeit-Lookup über `deps`; Testlauf nach jedem Schritt |
| Spec ändert sich unbemerkt (Reihenfolge, Beschreibungen) | Charakterisierung: `openapi.json` und Routentabelle von 2.1.1 als Referenz, Vergleich nach dem Umbau |
| Zirkuläre Importe | Richtung `main → api → services`; Mixins importieren nichts aus `llm_service`/`repository_service` |
| Widget überschreibt das Original-Backend | Deploy nur mit `--target` |
| Bundle verhält sich anders | Karma-Specs, Build, Bundle-Version 3.0.0; Browser-Tests laufen in der CI |
